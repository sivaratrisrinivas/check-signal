Memo: check-level results in the public feed

Srinivas Sivaratri · one page · data from Dan's Editorial Checks by Every, read 10 Oct 2026, 10:36 IST

The user problem

Someone picking a model sees one score per model. The score can't say which of their standards it reflects. On Dan's Editorial Checks, 12 of 34 checks give every model the same result, and a 80% tie on personal-benchmark-paragraph-revision hides different misses. The check-level data that shows this is public, but only in HTML run pages.

The proposal

Add check-level results to the JSON feed. Keep every v1 field. Under each run, list cases, and under each case, list checks with id, kind (code or model), scope, result and a short evidence string. Example generated from today's data.

Why it matters for a platform: the role description talks about a platform people can build on (cases, checks, runs, results). Check-level data is what outside tools need: a release-day "should I switch?" card, a saturation alarm, a judge spot check.

What I built, and what I cut

  • Built: a rules-only page that finds same-result checks, ties that hide different misses, and data oddities, plus a check-by-check "switch?" card. It reproduces every public scoreboard cell from the run pages.
  • Cut: LLM features, re-running models, auth, writing back to Checks. Rules answer these questions exactly, and saying so is part of the product call.
  • Limits: one run per cell, so variance is flagged, not measured. "Same result" is treated as a question, since some checks are floors on purpose.

Questions I would ask with internal data

  • Are the always-pass checks intentional floors? Is the always-fail check tracking a known gap, or is it stricter than intended?
  • Where does the flagged phrase on tend-feed-card-writing come from? It isn't in the public answer files I could download.
  • Are the low or missing token counts on some Opus 5.5 runs complete?
  • How long does a benchmark tuning review take today? That decides how much time this saves.

How I'd measure it in the product

  • Share of checks that separate models, per benchmark, over time.
  • Share of benchmarks where a flag is acted on within a week.
  • "Switch" decisions later reversed (the failure metric).
